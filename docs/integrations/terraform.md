# HashiCorp Terraform

CALM Forge sits *left* of HCL. The CALM spec is the upstream contract; Terraform HCL is one of the governed artifacts compiled from it, alongside Vault policies, Ansible inventory, Backstage catalog entries, OPA Rego, and DCM application config. Generated HCL is structured to align with Terraform Stacks — components and deployments — and ships with a signed Attestation BOM that links every emitted resource back to the declared intent it manifests. The intent for "which workload, which region, which capability set, which compliance scope" is authored once in CALM and projected deterministically into HCL; the same compilation can be re-run to detect spec-level drift before any Terraform plan executes.

On the Day 2 side, CALM Forge reads `.tfstate` as an intake source. The Terraform intake pipeline walks the state file, resolves each resource to a workload and a region (via tag conventions, attributes, or AZ extraction), and writes Placement nodes into the knowledge graph. Those Placements then feed the drift evaluator: declared capabilities and allowed regions are compared against what is actually deployed, with violations surfaced as findings with structured remediation proposals. Terraform remains the execution engine and the owner of state. CALM Forge does not write to state, plan against it, or shadow it. It reads it, semantically labels what it finds, and closes the loop back to declared intent so that the gap between "what we asked for" and "what is running" is visible and actionable.

The HashiCorp Terraform Stacks model and Sentinel-gated plan-and-apply remain the network and infrastructure control plane. CALM Forge upstream of that control plane provides one authored source of intent across all the LOBs and engines it touches; downstream of that control plane it consumes the resulting state as evidence. The integration is additive: existing Terraform workflows do not change, and Stacks-native consumers continue to operate exactly as they do today.
