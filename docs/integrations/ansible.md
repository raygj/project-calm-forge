# Red Hat Ansible Automation Platform

CALM Forge generates Ansible inventory from declared workload intent. The workload's components, regions, declared capabilities, and compliance scope are projected into structured inventory files — host groups, variable assignments, and group-level metadata — that AAP can consume directly. The same CALM spec that produces Terraform HCL produces the Ansible inventory describing how the resulting infrastructure should be configured, with provenance linking every host group back to the workload that authorized it. Inventory generation is deterministic: re-running the compilation against an updated spec produces an updated inventory, and the diff is auditable at the inventory layer rather than requiring a full plan-and-apply cycle.

On the Day 2 side, AAP is one of the primary intake sources for the knowledge graph. The Ansible intake pipeline reads job execution records, host inventory state, and configuration drift signals, and writes Placement nodes carrying `capabilities_granted` derived from the observed configuration. The `manifests_as` edge — the lifecycle boundary from declared Workload to deployed Placement — is populated here. Event-Driven Ansible signals trigger the post-deploy drift check automatically: when a job completes, CALM Forge evaluates the resulting placement against declared intent, writes the drift state, and feeds the reconciliation loop. The structured RemediationProposal that returns from reconcile can patch the inventory generation upstream, closing the loop back to authoring.

Ansible remains the configuration authority, the execution surface for inventory-based automation, and the Day 2 observation source for host-level state. CALM Forge does not author plays, gate AAP, or shadow the inventory it generates. It compiles intent into inventory, observes what runs through AAP signals, and writes the resulting evidence into the graph.
