# Backstage / Red Hat Developer Hub

CALM Forge generates Backstage Software Catalog entities directly from the knowledge graph. ExecutionEnvironments project to `Resource` entities of type `kubernetes-cluster`; Workloads project to `Component` entities of type `service`; Placements fold into the Component as aggregated drift status and `dependsOn` relationships derived from the `manifests_as` edge. The CNCF v1alpha1 catalog API is the only surface used — no Backstage extensions are required to render the base entities. Every entity carries `calm.io/` annotations that surface declared capabilities, granted capabilities, compliance scope, drift status, last evaluation timestamp, and provenance. Operators using Red Hat DevHub or community Backstage see what is declared, what is running, and whether the two are in sync, directly in the catalog UI they already use — without a separate dashboard.

The catalog file is one of the governed artifacts emitted on each compilation pass. The same CALM spec that produces Terraform HCL and Ansible inventory produces the `catalog-info.yaml` that publishes the workload to the developer portal. On the Day 2 side, CALM Forge reads the catalog back as an intake source: an established Backstage installation with `calm.io/`-annotated entities can re-seed a fresh knowledge graph, supporting environment bootstrap and disaster-recovery scenarios where the graph needs to be reconstructed from what CALM Forge itself has written. This is the output-as-input round-trip — the developer portal becomes both a publication surface and a memory.

Backstage and DevHub remain the developer portal and the operator-facing UX. CALM Forge does not own the portal, write plugins, or duplicate the catalog model. It compiles intent into catalog entities and reads catalog state back as evidence.
